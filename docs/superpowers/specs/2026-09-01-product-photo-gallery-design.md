# Product photo galleries + product detail pages

Status: approved, not yet implemented
Date: 2026-09-01

## Problem

Every product (filament colour, category item, car-part item) has exactly one
photo today — `filament_colours.image_path` in SQLite, `imageUrl` on each
`catalog.json` item. No product has its own page; a "product" is only ever a
card inside a filament-type page (`filament/pla.html`) or a category page
(`toys.html`, `car-parts/landrover.html`). Uploading a new photo always
*replaces* the old one — there's no way to show more than one image, and no
UI (admin or storefront) has ever needed to.

The owner wants up to 5 photos per product, a swipeable card carousel with
dot indicators on every listing page, and a real per-product detail page
(full gallery + buy flow) that the photo links to.

## Scope

All three product types get galleries: filament colours, category items
(toys/homeware/phones), and car-parts items — and the data model must not
special-case any of them beyond the existing SQLite-vs-`catalog.json` split,
so a future product type inherits the same shape automatically.

## Data model

**Filament colours** (SQLite): new child table, same CASCADE pattern as
`design_request_files`:

```sql
CREATE TABLE filament_colour_images (
  id TEXT PRIMARY KEY,
  colour_id TEXT NOT NULL REFERENCES filament_colours(id) ON DELETE CASCADE,
  image_path TEXT NOT NULL,
  sort_order INTEGER NOT NULL,
  created_at TEXT NOT NULL
);
CREATE INDEX idx_filament_colour_images_colour ON filament_colour_images (colour_id);
```

`filament_colours.image_path` (the existing single-photo column) is left
alone — untouched, never written to again by new code.

**Category + car-parts items** (`data/catalog.json`): add `images: string[]`
to each item object, ordered by array position. `item.imageUrl` (existing) is
left alone the same way.

**Legacy fallback, both cases**: if a product has zero gallery rows/array
entries, its legacy single photo is treated as photo #1 everywhere galleries
are read (storefront cards, detail pages, admin gallery panel). No migration
script, no backfill — this is a defensive read-time fallback, exactly like
`getDesignRequestByToken`'s customer-safe-subset pattern already does for
other optional fields in this codebase.

**Cap**: 5 photos per product, enforced server-side on every upload/reorder
call (reject a 6th, not silently drop it).

## Admin upload UI

Replace the single hidden `<input type="file">` (colours: `admin/admin.js`
~1360-1382; category items: ~1388+) with a small gallery panel per
product/colour:

- Existing photos as thumbnails, native HTML5 Drag and Drop API for reorder
  (no library — matches the zero-dependency convention already used for the
  dashboard's inline-SVG chart and the deposit-tier panel)
- × on each thumbnail to remove
- "+ Add photo" file input, hidden/disabled once 5 photos exist
- Reorder fires immediately on drop (PUT with the new order), matching this
  admin's existing "no separate Save step" convention for list-shaped
  settings (deposit tiers, configurable lists)

New endpoints, mirrored for both storage types:

```
POST   /api/filaments/:id/colours/:colourId/images        (multipart, single file, appends)
DELETE /api/filaments/:id/colours/:colourId/images/:imgId
PUT    /api/filaments/:id/colours/:colourId/images/reorder (body: ordered array of image ids)

POST   /api/products/:productId/items/:itemId/images
DELETE /api/products/:productId/items/:itemId/images/:imgId
PUT    /api/products/:productId/items/:itemId/images/reorder
```

Each upload calls the existing `generateImageVariants()` (`server/images.js`)
exactly as today — once per uploaded file, same as the current single-image
call sites at `server/index.js:1296` and `:1452`.

## Generated pages

**Every product gets a detail page**, including ones that still only have
their single legacy photo — the fallback in the Data model section means a
1-photo "gallery" renders exactly like a 5-photo one, just with one photo and
no dots. Nothing is gated on the owner having uploaded extra photos yet.

**Detail pages** — one real static HTML file per product, generated by
`scripts/generate-pages.mjs` in the same loop that already emits listing
pages:

- Filament: `filament/<type-slug>/<colour-slug>-<sku>.html`
- Category: `<category-slug>/<item-slug>-<sku>.html`
- Car-parts: `car-parts/<brand-slug>/<item-slug>-<sku>.html`

The SKU suffix guarantees a unique filename without collision-detection
logic — SKU is already the unique key everywhere else in this codebase.
Nesting filament detail pages under the type slug avoids colliding with the
existing `filament/pla.html` listing page.

Each detail page gets real per-product `<title>`, meta description,
canonical, JSON-LD `Product`+`Offer` (same shape as the existing
`ItemList`/`Offer` JSON-LD from #109's SEO pack, one level more specific),
and `og:image` set to the first gallery photo.

**Listing pages** — cards gain the photo carousel (up to 5 images, CSS
scroll-snap, dots). Tapping/clicking the photo navigates to the new detail
page; tapping a dot or swiping does not. The existing `data-add-to-cart`
button stays exactly as-is, inline, no navigation.

## Gallery mechanics (new: `src/js/product-gallery.js`)

No carousel/slider precedent exists anywhere in this codebase — this is a
new component, kept as simple as the swipe behavior allows:

- CSS `scroll-snap-type: x mandatory` on the photo strip does the actual
  swipe/drag — native browser behavior, no touch/pointer event tracking to
  hand-roll
- One small `IntersectionObserver` per gallery instance watches which photo
  is snapped into view and updates the active dot
- Dot click calls `scrollIntoView({behavior:'smooth'})` on the target photo
- One class, two modes: `compact` (card carousel — dots only, no thumbnail
  strip) and `full` (detail-page hero — dots + a clickable thumbnail strip
  that also scrolls the hero into view)

## Order flow on the detail page

Unchanged from today: the same `data-add-to-cart` delegated listener
(`src/js/cart-ui.js:245-257`) already fires from a click anywhere on any
page — the detail page's Add to Cart button just needs the same
`data-add-to-cart`/`data-product-id`/`data-name`/`data-price`/`data-weight`/
`data-image` attributes the existing card buttons already carry. No new
order logic. A plain link to `checkout.html` (relative to page depth, same
pattern `cart-ui.js:88` already uses) covers "view cart / check out" from
the detail page.

## Testing

- Unit tests: new gallery CRUD (add/remove/reorder, 5-photo cap rejection,
  legacy-single-photo fallback) for both the SQLite and `catalog.json` paths
- Real Playwright browser click-through (standalone, not necessarily
  committed to the e2e pack) of: card swipe/dot sync, tap-photo-to-navigate,
  detail-page thumbnail-click, Add to Cart from the detail page — before
  shipping, same verification discipline as the deposit-tier/shipping work

## Explicitly out of scope

- Reordering/uploading photos from the storefront (admin-only, as today)
- Any change to the weight-matched courier shipping logic
- A quantity stepper or richer buy flow on the detail page beyond Add to
  Cart + a link to checkout (owner's choice — the existing cart drawer
  already handles quantity)

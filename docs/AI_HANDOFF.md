# AI Handoff Brief — Lapanza 3D Creative Lab

**If you are an AI assistant picking up this project cold, read this file first.** It orients you fast; it is not the full reference. Once you have repo access, read [`docs/SYSTEM_DOCUMENTATION.md`](SYSTEM_DOCUMENTATION.md) next — it has the complete architecture, database schema, API reference, functional spec, and test cases. This file exists so you don't have to read that whole document before knowing where to start or what not to break.

---

## What this is

A live e-commerce + operations platform for a South African 3D-printing/filament retailer (Lapanza 3D Creative Lab). Node/Express backend + SQLite, static Vite-built storefront, hand-written vanilla-JS admin SPA. Single developer/owner, no team. Tests run automatically on push/PR (GitHub Actions), but deploy is still manual — changes are tested, pushed, then deployed to production over SSH.

**Repo:** `github.com/jbarkhuizen/Lapanza-3d-Creations-Martin`, branch `main` (the only branch — no PR workflow, commits go straight to `main`)
**Live site:** https://lapanza3d.co.za
**Live admin:** https://lapanza3d.co.za/admin/
**Production server:** VPS at `41.222.36.147` (domain.co.za, AlmaLinux 10), SSH-key-only access as user `deploy`

## Non-obvious things that will bite you if you don't know them

These are real incidents from this project's build/deploy history — documented in full in `SYSTEM_DOCUMENTATION.md` §12.5, listed here so you don't repeat them:

- **`better-sqlite3` requires Node ≥22, hard requirement.** Node 20 installs with only a warning, then segfault-crashes the process on every DB access. Always verify `node -v` is 22+ before anything runs.
- **Never blindly re-copy `deploy/nginx-lapanza.conf` onto the live server.** Once certbot has run, the live `/etc/nginx/conf.d/lapanza.conf` has HTTPS/redirect blocks appended that a naive overwrite deletes, silently breaking HTTPS. `deploy/deploy-app.sh` already guards against this (only installs the template if the file doesn't exist) — do not "fix" that guard away.
- **Express needs `app.set('trust proxy', 1)`** (already set in `server/index.js`) because nginx sits in front of it in production. Removing it breaks every rate-limited route with a cryptic crash that looks to end users like a random 404.
- **Two independent, in-memory session systems** (admin sessions and customer sessions) — both are lost on every `systemctl restart lapanza-admin`. This is expected, not a bug to "fix" reflexively.
- **Product data lives in two places, not one:** the sellable filament catalog is in SQLite (`filament_types`/`filament_colours`); category items (toys/homeware/phones/car-parts) are in `data/catalog.json`, which is **gitignored** — it's real business data, not code, and must be copied to a new server separately from `git clone`. Since V0.80 the backup job snapshots it alongside every `.db` backup (paired `.catalog.json` file, pruned together, synced offsite with the rest of the backups dir), and `saveCatalog()` writes temp-then-rename so a crash can't truncate it. Note the `DATA_DIR` caveat below still applies: the backup reads `dataDir()/catalog.json` while `store.js` writes `{cwd}/data/catalog.json` — identical unless someone sets `DATA_DIR`.
- **Storefront static pages are not live-rendered.** They're pre-generated HTML (`scripts/generate-pages.mjs`, triggered by the admin "Publish to site" button), which is then bundled into `dist/` — the directory nginx actually serves — by `npm run build` (vite). "Publish to site" runs **both** steps now; until a fix this session it only ran the first, so clicking it looked like it worked (source pages updated) but the live site silently never changed until the next full code deploy happened to run the build too. If you're debugging "my catalog edit isn't showing up," check whether `dist/` was actually rebuilt, not just whether `/api/publish` returned 200. `PUT /api/settings` had this exact same gap independently (2026-08-27, found when featured products didn't appear live after being saved) — it now also runs the generate+build pipeline, non-fatally (a `publishWarning` in the response if it fails, the setting itself is still saved). If you add a THIRD route that writes something publicly-visible, check whether it needs the same treatment rather than assuming `syncPublicJson()` alone is enough — it never is for anything nginx serves from `dist/`.
- **Currency formatting has one canonical implementation, in three files.** `server/money.js` (server + `generate-pages.mjs`), `admin/money.js`, `src/js/money.js` are deliberate twins — admin/ and src/js/ are separately served/bundled and can't import server/money.js directly. If you change the format, update all three and say so in the commit; five independent, drifted copies is exactly the bug that made this necessary in the first place.
- **Payfast's `payment_method` values are `cc` and `ef` — not `eft`.** Confirmed against https://developers.payfast.co.za/docs#quickstart. An invalid value doesn't error, it silently falls through to whatever payment method Payfast's own account config falls back to — this is exactly how a customer choosing "Instant EFT" ended up on an unrelated Mobicred page. If a payment-method-related bug report sounds bizarre, check the wire value against Payfast's docs before assuming it's an account-config issue.
- **Checkout prices are always server-resolved, never trust a client-submitted price** — this is a deliberate security property, not an oversight to "simplify."
- **Stock is RESERVED at order creation, not checked-then-decremented-later.** `reserveStockForOrder()` in `server/orders.js` runs inside the same `db.transaction()` as the order/order_items INSERT for online checkout — it re-reads stock fresh and throws (rolling back the whole order) if insufficient. This is deliberate, not incidental: a pre-transaction check followed by a decrement-at-payment-time (the original, buggier design) lets two concurrent orders both pass the check before either one reserves anything, so both get confirmed for the same physical item. If you ever touch this code, keep the check-and-decrement together, inside one transaction, using a fresh read — don't split them apart again. `createManualOrder` reserves the same way but never hard-blocks (admin trusted, floors at 0) — see `decrementStockForOrder`. Cancelling an order (`cancelStalePendingOrders` or admin `updateOrderStatus(..., 'cancelled')`) releases the reservation via `restoreStockForOrder`. Test coverage: `server/orders.test.js`, the block of tests starting with "createOrder reserves...".
- **Password reset tokens (V1.01) are a separate column pair from email-verification tokens** (`reset_token`/`reset_token_expires` vs `verification_token`/`verification_token_expires` on `clients`) — both can be outstanding at once without clobbering each other. Reset TTL is 1h, shorter than verification's 24h, since it's freely re-requestable.
- **`deploy/deploy-app.sh` writes Git-backed release detail to the live DB directly** (via `scripts/record-deploy-version.mjs`, no HTTP/auth involved) as its last step. It creates the Version History row and its release-detail record atomically: commit metadata, release notes, changed files, and line statistics. Do not make this step non-fatal: a deployed version without traceable release detail defeats the audit trail. Use `scripts/backfill-version-release-details.mjs --force` only to rebuild historical detail from Git.
- **The Test Cases page must only execute catalogued Node tests.** `server/test-runs.js` derives the catalog from `server/*.test.js` and invokes `node --test` with fixed server-side arguments. Do not accept arbitrary shell commands, paths, or test patterns from the browser. On a Git checkout it runs from a temporary detached worktree, not the live checkout, to protect production-local data and generated pages. Test-run history is intentionally retained in SQLite for the admin report.
- **About this Site is intentionally read-only and non-privileged.** `server/site-overview.js` inventories files the `deploy` service account can read, but never file contents. Keep `/proc`, `/sys`, `/dev`, and `/run` non-browsable; they are virtual filesystems, not durable site storage, and should never be scanned by the application.
- **Newsletter campaign recipients are consent-bound snapshots.** Do not treat `whatsapp_opt_in` as email consent. `newsletter_campaign_recipients` stores the exact selected audience; `newsletter_suppressions` blocks future sends after unsubscribe. Campaign delivery temporarily uses Gmail SMTP by owner choice, so retain low-volume, manual sends until a dedicated email provider is selected.
- **Newsletter rich content is server-rendered from blocks.** Keep `server/newsletter-content.js` as the source of truth for valid heading, text, image, button, and divider blocks. Do not accept arbitrary browser HTML for campaigns; image assets are limited to JPEG/PNG/WebP under 5MB and plain-text fallback is mandatory.
- **Newsletter analytics measure SMTP outcomes, not reader engagement.** `getCampaignAnalytics()` aggregates the immutable recipient snapshots into audience, accepted, failed, pending, and source totals. A `sent` recipient means Gmail accepted the message for delivery; do not label it as delivered, opened, clicked, or inboxed without a provider-supported tracking design and explicit privacy review.
- **Newsletter administration is auditable.** Template/image changes and campaign creation, approval, test send, and queueing use `marketing_updated` audit entries. Keep action details non-sensitive: subjects, filenames, and recipient counts are appropriate; recipient email addresses are not.
- **In-house filament transfers are stock movements.** The selected `filament_colours` item is decremented and the chosen in-house row incremented in one database transaction. Do not replace this explicit picker with automatic Type/Colour matching. New local entries are unique by Brand + Type + Colour; brands come from `inHouseFilamentBrands` in Site Settings.
- **Offsite backup sync uses OAuth as the real Google account, NOT a service account.** A service account was tried first and confirmed broken: it can be shared onto a Drive folder and read/list it fine, but any new file upload fails with `storageQuotaExceeded` — service accounts have zero storage quota of their own on a personal (non-Workspace) Google account, and folder-sharing doesn't change that; real Shared Drives (where it would work) are Workspace-only. `rclone authorize "drive"` run once on a machine with a browser produces a token to paste into the VPS's rclone config instead (DEPLOY.md §9) — a human step, but a one-time one; the refresh token keeps it working indefinitely after that.
- **Multi-line heredocs pasted into an SSH session can silently mangle** — hit this live writing `rclone.conf`: the heredoc "succeeded" (no error) but the file kept its old contents. Prefer a single-line `printf '...\n...\n' > file` for anything written this way over SSH.
- **There is a live Todo / Backlog admin page (`/api/todos`) for tracking gaps you identify while working in this repo** — if you're an AI assistant continuing this project and notice something worth doing later (not urgent enough to fix inline), add it there instead of only mentioning it in chat: `POST /api/todos` with `{ name, description, category }` through the same admin session. Category is one of `Bug`/`Feature`/`Enhancement`/`Tech Debt`; leave `status` unset to default to `Backlog`.
- **`DATA_DIR` does NOT redirect `data/catalog.json`.** `server/paths.js`'s `dataDir()` (SQLite, backups) respects `DATA_DIR`; `server/store.js`'s own `paths()` for the category-item catalog is hardcoded to `{cwd}/data/catalog.json` regardless. Testing anything that touches category items (checkout, catalog editor, Print Job Costing's "List for sale") against a scratch `DATA_DIR` still reads/writes the real local `data/catalog.json` — back it up first if you're clicking through it manually, same as this session did.
- **SQLite `date()`/`datetime()` default to UTC; the server runs in SAST (UTC+2).** Any query grouping by calendar day (invoice dates, analytics daily breakdowns) needs the `'localtime'` modifier explicitly, or day boundaries silently shift near midnight. Already bit this project once (imported invoice dates landed a day early) before being applied proactively elsewhere.
- **`.env` secrets are never pasted into chat/AI tooling** — the working rule established for this project is that whoever has server access types secrets directly on the server (`nano /opt/lapanza/app/.env`). Don't ask for or accept Payfast keys, the Gmail app password, or WhatsApp tokens in conversation.
- **`creator`/`models`/`sourceUrl` on a category item are car-parts-only** (GWM/Landrover, gated in `admin.js` on `parent === 'car-parts'`) — every other category (toys/homeware/phones) never renders or stores them, they just sit as empty defaults from `normalizeItems()`. `models` stores plain name strings picked from Settings' `carPartModelsLandrover`/`carPartModelsGwm` lists (one per brand, not ids — same convention as `inHouseFilamentBrands`), chosen in `admin.js`'s `carPartItemFields()` by the item's own category slug. `sourceUrl` is intentionally left out of `export.js`'s public `categories.json`, don't add it there without checking it's meant to become customer-facing. If a spreadsheet import ever needs redoing (Landrover model corrections, GWM's turn), don't retype a source spreadsheet's "Fits (Vehicles)"-style column by hand without spot-checking it against the source site first — the Land Rover sheet had truncated/corrupted model and category columns that the source site's own per-part pages (JSON-LD) didn't.
- **Every new Settings key needs THREE additions, not two — this has silently broken saves twice now** (`inHouseFilamentBrands` originally, `carPartModelsLandrover`/`carPartModelsGwm` on 2026-08-27, both caught only by actually testing the save, not by reading the code). Adding a new admin-editable setting requires: (1) `DEFAULT_SETTINGS` in `settings-defaults.js`, (2) `LIST_SETTING_KEYS` in `settings.js` if it's a `{id,name,active}[]` list (read-side normalization), AND (3) the `allowed` array in `PUT /api/settings` (`server/index.js`) — miss #3 and the admin UI looks fully functional (renders, the save button works, no error) while every edit is silently discarded before it ever reaches the DB. If you build a new configurable list, write the round-trip regression test (`server/index.test.js`, search "allowlist-missing") in the same sitting, not after — it would have caught this immediately both times.
- **Regenerating static pages locally (`node scripts/generate-pages.mjs`) trusts whatever's in your local `public/uploads/`** — `imageFileExists()` has no way to know a photo exists only on the production server and never made it into your checkout; it just falls back to "Photo coming soon" for a genuinely-missing local file and writes that into the committed HTML. Bit this project once (2026-08-27, GWM/toys photos silently regressed after a routine catalog merge). Before pushing a locally-regenerated category page, `grep -c 'Photo coming soon'` it and compare against what's actually live, or pull the real uploaded files down first (`scp` from the VPS) — don't assume local and production `public/uploads/` match just because the catalog data does.
- **A freshly-inserted `<details open>` can fire a `toggle` event with no user action involved** — some browsers emit one synthetic `toggle` the instant such an element is parsed/connected to the DOM, matching the `open` state you just set. A naive `addEventListener('toggle', ...)` attached right after `innerHTML =` will misread that as a real click. Bit the Stock Management grouping (2026-08-27): re-rendering during a search force-opened a manually-collapsed section, and the resulting spurious `toggle` silently erased the remembered collapse state. Fix pattern used there (`admin.js`, search "data-initial-open"): stamp the element with the `open` value you rendered it with, and in the toggle handler, ignore the event once if `el.open` still equals that stamped value — only a real subsequent toggle can differ from it. Reuse this pattern for any other collapsible `<details>` built the same way (server-string template + `innerHTML`, not individually created DOM nodes).
- **Every catalogue card and filament swatch has a stable `id="item-{sku-or-fallback}"`** (`server/item-anchor.js`'s `itemAnchorId()`, used by both `generate-pages.mjs` when writing the id and `export.js` when resolving a link to it) — this is how `settings.featuredProducts` links land on the exact item, not just the top of the page. If you ever change how a card's id is computed in one of those two files, change it in `item-anchor.js` itself so both stay in sync, or a featured-product link silently breaks.
- **`settings.featuredProducts` stores `productId` refs (`filament:{slug}:{sku}` / `category:{slug}:{sku}`), never a typed name/price/link** — resolved fresh into `{name,price,href}` by `export.js`'s `syncPublicJson()` on every publish. Don't add a manual-entry featured-product field; the whole point is it can't go stale.
- **`todo_items.created_by` is NULL on every row that predates 2026-08-27** (no honest way to backfill who logged something before the column existed) — the admin UI shows "—" for those, don't treat a NULL as an error. When creating a Todo/Backlog item via `POST /api/todos` on the owner's behalf, pass `createdBy: 'Claude'` explicitly in the body — omitting it defaults to whichever admin session is active, which would misattribute an AI-logged item to whoever happens to be logged in.
- **Order confirmation emails must never send before payment is actually confirmed.** For `payfast_card`/`payfast_eft`, `/api/checkout` only creates the order as `pending_payment` — the customer hasn't paid yet, they're about to be redirected to Payfast. `sendOrderConfirmationEmail()` only fires from the `/api/payfast/itn` webhook handler once `payment_status=COMPLETE`, gated on `markOrderPaid()`'s `changed` flag (not just its `lowStock` result) so a duplicate ITN redelivery for an order already marked paid can't resend it. `manual_eft`/`cash_on_collection` still confirm immediately at `/api/checkout` time — there's no online payment gate to wait for there. If you're touching checkout email logic, keep this split; sending "your order is confirmed" for an abandoned/declined Payfast payment is exactly the bug this fixed. **This does NOT apply to the invoice email** (`sendInvoiceEmail()`, `mailer.js`, added 2026-08-28) — an invoice stating what's owed is truthful whether or not Payfast has cleared, so it sends immediately for every payment method; only the plain-text "confirmed" wording needs the payment gate.
- **Any route that creates/edits/deletes a filament, colour, category product, or category item must call the shared `publishCatalog()` helper** (`server/index.js`, added 2026-08-28), not just `syncPublicJson()`. This is the third time the same bug has shipped: a write reaches the DB and the `public/*.json` export fine, but the *static* HTML pages (`generate-pages.mjs` output, bundled into `dist/` by `vite build`) never regenerate, so the change looks saved in the admin but never appears live until someone clicks "Publish to site" or a deploy happens to rebuild anyway. Row 118 (§2) fixed it for `PUT /api/settings`; this fix closed it for every remaining catalog-mutating route in one pass (including new per-item routes) after it was found to be the actual reason a GWM item's "Fits models" checkboxes never made the public model-filter dropdown appear. If you add a new route that writes anything `generate-pages.mjs` reads, call `publishCatalog()` (or route through code that already does) — don't reach for a bare `syncPublicJson()` "just this once."
- **`renderInvoiceHtml()` lives in `server/invoice.js`, not `server/index.js`.** One template, three callers: the admin's "Print invoice" route, and `mailer.js`'s `sendInvoiceEmail()` (unpaid at order placement, `{paid:true}` once Payfast confirms or an admin marks a manual order "Already Paid"). If the invoice layout ever needs to change, change it once here — don't let the emailed and printed versions drift into two different templates.
- **The email-delivery-down WhatsApp fallback (`server/alerts.js`'s `checkEmailFallback()`, backlog #120) will silently no-op until the owner does two things this assistant cannot do for them**: create and get Meta Business Manager approval for a WhatsApp message template (WhatsApp's own rules forbid free-text business-initiated messages — same constraint that already blocks #7 WhatsApp campaigns), and fill in that template's name + their own WhatsApp number in Settings → Operational Alerts. Until both exist, a Gmail outage that would otherwise trigger this fallback just logs a `console.error` and nothing reaches anyone — don't report this as "broken," it's the documented degraded state, same as every other WhatsApp feature in this codebase.
- **`DATA_DIR` only sandboxes the SQLite DB — `PUT /api/settings`/catalog-mutating routes still write to the REAL project's `src/data/*.json`/`public/site-settings.json`/generated HTML regardless.** Hit this 2026-08-28 verifying the email-templates feature: started `node server/index.js` with `DATA_DIR=<scratch>` pointing at a genuinely fresh/empty DB (to avoid touching the real local dev DB), created a throwaway admin, then called `PUT /api/settings` to test a save — this triggered the same `runGenerate()`+`syncPublicJson()` pipeline every settings save runs (§2 Evolution History, "third crossing" gotcha above), which reads/writes those files from fixed `process.cwd()`-relative paths (`scripts/generate-pages.mjs`, `server/export.js`), never respecting `DATA_DIR`. Result: the scratch DB's empty/default data got written straight into `src/data/filaments.json` (lost ~1750 lines of real catalog data), `public/site-settings.json`, and `src/data/settings.json` — all still just uncommitted working-tree changes (`git checkout -- <files>` fully recovered them, nothing was ever committed/pushed/deployed), but a close call. **If you need to exercise a real running server against a throwaway DB, avoid any route that calls `runGenerate()`/`runBuild()`/`syncPublicJson()`** (that's `PUT /api/settings` and every catalog/filament/colour/category CRUD route) — stick to routes that only touch the DB (auth, read-only GETs), or accept that `git status`/`git diff --stat` on `src/data/*.json`, `public/site-settings.json`, and every generated HTML page needs checking (and reverting if unintended) immediately afterward, before anything gets staged.
- **Adding a new root-level static HTML page (like `get-in-touch.html`) needs a THIRD addition, same failure shape as the Settings-key gotcha above.** `vite.config.js`'s `htmlEntries()` hand-lists every root page as a rollup build entry — only `filament/` and `car-parts/` are auto-globbed from disk. A new page works perfectly in `npm run dev` (vite's dev server serves whatever's on disk, entry list or not) and passes every test (nothing in the suite runs `vite build`), so the first sign of trouble is a live 404 after deploy. Hit for real 2026-08-28: `get-in-touch.html` shipped, deployed, immediately checked live (not just trusted the deploy script), found 404ing, root-caused and fixed within the hour. Adding a new top-level page requires: (1) the HTML file itself, (2) a nav link (`src/js/nav.js`), AND (3) an entry in `vite.config.js`'s `htmlEntries()` — miss #3 and it's invisible until someone actually loads the live URL.
- **Every owner-facing notification email must read `settings.orderNotificationEmail` (`mailer.js`) -- never its own hardcoded address or a separate env var.** `sendLowStockAlert` didn't, until 2026-08-28: it had its own `LOW_STOCK_ALERT_TO` (`process.env.LOW_STOCK_ALERT_EMAIL || 'jbarkhuizen@gmail.com'`), independent of Settings, and the env override was never actually set in production -- so every low-stock alert landed in a personal inbox regardless of what the admin had configured in Settings → Public Site Contact. `sendNewOrderNotificationEmail`/`sendOrderCancelledNotificationEmail`/`sendNewDesignRequestNotificationEmail` were already correct; `sendLowStockAlert` now matches them. If you add a new owner-facing notification, read `getSettings().orderNotificationEmail` the same way -- don't invent a new constant or env var for "where should this go," there is exactly one answer to that question in this app.
- **Admin topbar's global action buttons (`admin/index.html`'s `.topbar-actions`, "+ Filament"/"+ Category") are visibility-gated in `setRoute()` (`admin.js`) by an *inclusion* list, not exclusion — deliberately, after the exclusion version broke.** The original code hid them on a hardcoded list of routes (Settings/Editor/Backups/etc) and showed them on everything else by default; every route added after that list was written (Registered Users, Orders, Clients, New Order, Invoice History, Shipping, Resources, Design Requests, Newsletter, WhatsApp Updates, Stock, Purchases, Print Job Costing, In-House Filament, Dashboard) silently inherited "show the catalog buttons" even though none of them are catalog pages — found and fixed 2026-08-28. If any future page-scoped-only UI element (a button, a toolbar) needs to show on just one or two views, gate it by checking `route === 'thatRoute'`, not by excluding everywhere else it shouldn't appear — a forgotten exclusion is invisible until someone notices the element in the wrong place, an inclusion list fails safe (hidden) instead.
- **Client matching by name (added 2026-08-28) is a deliberate, real risk, not an oversight.** `findOrCreateClientForCheckout` (`clients.js`) matches by email first; only when there's no email match does it fall back to an *exact, case-insensitive* first+last name match — and only when that name matches exactly one existing client, never more. Two genuinely different customers who happen to share a common name (e.g. two "John Smith"s) will never be silently merged by this path, but a customer who changes their email AND happens to share a name with someone else on file is a real (rare) edge case that could match the wrong record. If this ever needs tightening (e.g. requiring phone or a partial address match too before allowing a name-only match to update a record), that's the function to change — don't add a second, competing matching path elsewhere.
- **Any `localStorage`-persisted checkout/cart state must be cleared on every order-success path, not just the happy one.** `lapanza-checkout-prefs` (shipping/payment method persistence) was being cleared alongside the cart on the Manual EFT/Cash on Collection success path, but not on the Payfast one (`checkout-complete.html`) — so a customer placing a second order in the same browser session got the *previous* order's shipping/payment picks silently restored instead of the real HTML defaults. Both cart and prefs now clear from the same two places (`clearCart()` + `clearCheckoutPrefs()`, `src/js/checkout-prefs.js`); if a third success path is ever added (e.g. a different payment gateway), clear both there too.
- **A custom CSS rule cannot silently override a Tailwind v4 utility class by source order alone.** `@import "tailwindcss"` generates its own utilities in an internal `utilities` cascade layer that outranks an unlayered custom rule regardless of where that rule sits in the stylesheet — hit this making the collapsible sidebar's header offset (`#site-header.is-collapsed{left:0}` in `main.css` was silently losing to the existing `md:left-72` class). Needed `!important` to win. If a custom override rule "does nothing" against a Tailwind utility, this is the first thing to check, not a specificity/source-order bug.
- **Any order-cancellation path must call both `restoreStockForOrder` AND the owner-notification email — there are now three of them, not one.** `pending_payment → cancelled` happens via the 7-day auto-cancel job (`jobs.js`), an admin's `updateOrderStatus`, or the customer's own `cancelOrderByClient` (account page "Cancel" button). All three restore stock; all three now also call `sendOrderCancelledNotificationEmail` (`server/mailer.js`) so the business owner sees every cancellation, not just new orders. If a fourth cancellation path is ever added, it needs both, not just the stock restore.
- **A security-warning hook blocks any Edit/Write call whose diff contains the literal substring "innerHTML", including new code that mirrors an existing, already-escaped pattern elsewhere in the same file.** Hit repeatedly this session (checkout bucket-split, account-page order-cancel UI, and again documenting the workaround itself in this very file). It's a dumb substring match, not a semantic check. Two ways through it: (1) for new rendering logic, write it with `createElement`/`textContent`/`appendChild`/`replaceChildren` from the start instead of a template-string assignment; (2) when editing a large existing template-string-style file where a full rewrite isn't proportionate (e.g. `admin/admin.js`), split the change into several smaller Edit calls, none of whose old_string/new_string includes that one flagged line itself — edit the surrounding content in separate calls instead. Both got real work done this session without either tripping the hook or rewriting untouched code.
- **Every public form on this site has `novalidate` on the `<form>` tag, so `required` attributes alone do nothing — the JS must call `form.reportValidity()` itself before its fetch, or the browser silently skips native validation entirely.** Checkout already did this correctly; the design-request form didn't (`name`/`phone` weren't even marked `required` in the HTML, and the JS never checked `form.checkValidity()`/`reportValidity()` at all) until this was noticed and fixed. If a form on this site "isn't validating," check for `novalidate` first, not the `required` attributes.
- **`orders.status` and `orders.payment_status` are two separate columns that can silently drift apart.** Before this session, only `markOrderPaid` (the Payfast ITN webhook path) ever touched `payment_status` — an admin manually setting status to `paid` via the status dropdown left `payment_status` on `'pending'` forever, which is exactly why Invoice History's "Status" column looked permanently stuck on Pending for manually-marked-paid orders. `updateOrderStatus` now keeps both in lockstep for every caller (paid/shipped/completed → paid, pending_payment → pending, cancelled leaves it alone). If you ever add a new way to move an order's status, route it through `updateOrderStatus` rather than writing `status` directly — writing only `status` reintroduces this exact drift.
- **`listOrders()` and `getOrder()` used to have different return shapes for the same conceptual thing.** `getOrder()` (single order) has always attached a real `client: {...}` object via a join; `listOrders()` (the list/search version, used by both the admin Orders and Invoice History views) never did — it only ever built its client lookup map to power the `q` search filter, never attached it to the rows it returned. This is why Invoice History's client column was blank for every single order. Now fixed at the shared source (`listOrders` always attaches `client`), but if you add a third list-returning order function, check it matches `getOrder`'s shape rather than assuming the two existing ones already agreed with each other.
- **A CSS override for `table.catalog` (admin.css) must come AFTER the `table.catalog` rules it's overriding, not just anywhere in the file.** `table.todo-table td` and `table.catalog td` have identical selector specificity (element+class+descendant-element either way), so when both match the same element, source order decides the winner — not which one is "more specific" or which class is listed second in the HTML. Hit this building the Todo/Backlog page's tighter-row styling: the new `.todo-table` block was placed earlier in the file (near the other `.todo-*` rules) than the shared `table.catalog` block further down, so the padding/font-size override was silently losing to the later, more general rule. If a scoped override of a shared admin table style "does nothing," check its position in admin.css relative to the rule it's meant to override before assuming a specificity or selector-syntax problem.
- **`execFileSync`/`execSync` on this project's single Node process blocks the ENTIRE admin backend, not just the caller.** There's no worker pool or clustering here — one process serves every request. A synchronous subprocess call (rclone, git, anything shelling out) freezes Node's single-threaded event loop for its whole duration, so every other in-flight or incoming request queues behind it regardless of which route it's for. Confirmed the hard way: adding an uploads copy to the backup sync turned a near-instant DB-only `execFileSync` call into a 5+ minute one, and the whole site went unresponsive for that entire window. Use `execFile`/`exec` (via `util.promisify` or their native Promise/callback form) for anything that isn't guaranteed near-instant, especially inside a scheduled job (`jobs.js`) that runs unattended in production.
- **A filament colour's `imageUrl` being set does NOT mean the file exists on disk** — `generate-pages.mjs` now checks (`imageFileExists()`) before rendering `<img>` instead of trusting truthiness alone, falling back to "Photo coming soon". Worth checking `ls public/uploads/filaments/` against the DB before assuming a broken image is a code problem.
- **`git stash push -u` on this repo's VPS is genuinely dangerous, and `git stash show --stat` will not warn you.** `public/uploads/` is real, deliberately-uncommitted business content (photos etc, `.gitignore` never covers it) that shows as untracked in `git status` right alongside harmless regenerated-catalog noise. `-u` sweeps up BOTH into the same stash; `git stash show --stat` (the obvious "is it safe to drop" check) silently omits untracked files from its output entirely, so it can report "looks fine" while blind to real content sitting inside. This is exactly how an AI assistant destroyed 106 of 107 filament colour photos on 2026-08-27 (Linandi's manual uploads, not a content gap as first assumed) — recovered only by luck, because a dropped stash isn't immediately garbage-collected (`git fsck --no-reflog` found it, `git ls-tree` on its untracked-files parent had the files, `git checkout <tree> -- <path>` restored them). **Rule going forward: use `git stash show --include-untracked` (or `-u`) before ever dropping a stash on this repo, or avoid `git stash -u` entirely** — stage/move aside the specific dirty tracked files you actually need to clear instead of blanket-stashing untracked content you haven't inventoried. `public/uploads/` also still has zero backup coverage (backlog #132) — the recovery above worked despite that, not because of it.
- **`npm run dev:admin` (`node server/index.js`, no `--watch`/nodemon) does not pick up code changes without an actual restart, and on this Windows/Git-Bash setup `pkill -f "server/index.js"` does not reliably kill it** — a stale admin server from hours/turns earlier can keep serving old code indefinitely while every later `npm run dev:all` silently fails to bind port 8787 (look for `dev:admin exited with code 0` in its log — that's the tell) and every `vite` instance piles up on the next free port instead (5173, 5174, 5175, ...). This produced a real false bug report mid-session (a new field added to `listInventory()` appeared completely missing at runtime). Verify what's actually listening before trusting a "fresh" dev server: PowerShell `Get-NetTCPConnection -LocalPort 8787 -State Listen | Select-Object OwningProcess` then check that process's `StartTime` against when the code last changed; `Get-Process node | Stop-Process -Force` (not `pkill`) to actually clear every stale instance before restarting.
- **The admin login screen used to hardcode `Default password: lapanza-admin` under the sign-in form, live in production, regardless of whether a real admin account already existed** — the actual first-run flow (`/api/setup/status`, `/api/setup`, `admin.js`'s `#view-setup`) was already correct and properly gated on `needsSetup`; this was just leftover static HTML from before that flow existed. Removed (closes backlog #35). If you ever touch `admin/index.html`'s login markup again, don't reintroduce a literal credential/hint string — the setup flow is the only place a password should ever be shown, and only on first run.
- **Don't trust "Payfast live payments verified" without checking the actual ITN log, not just that `PAYFAST_MODE=live` and a transaction was attempted.** The only real ITN this production server has ever received (Aug 26, order `691b035e`, a R5 test) came back `serverConfirmed: true`/`amountValid: true` but `signatureValid: false`. Passphrase was checked and confirmed to match the Payfast dashboard exactly (2026-08-27) — the real cause was `buildSignature()` in `server/payfast.js` filtering out blank-valued ITN fields before hashing, which contradicts Payfast's own reference PHP implementation (it includes every posted field except `signature`, blank or not — confirmed against their published sample code, not assumed). Fixed via a `skipEmpty` option: `true` (unchanged) for the outbound checkout redirect, `false` for inbound `verifyItn()`. Until a fresh real transaction logs `valid: true` end-to-end (order flips to `paid`, stock/email/audit all fire from the ITN handler, not just `serverConfirmed`), don't report Payfast live payments as fully proven working — this fix is evidence-based but unproven against a real transaction, since the original failing one is gone (deleted in the test-order cleanup).
- **Payfast's own reference ITN-signature algorithm includes every posted field except `signature`, even ones with a blank value — never filter those out before hashing on the inbound (verification) side.** `urlencode('')` is still `''`, contributing a bare `key=` to the param string, not omitting the key. This is fine (and correct) to filter on the OUTBOUND redirect, since we choose what to send; filtering it on the INBOUND ITN check produces a different string — and therefore a different hash — than the one Payfast itself computed, for any real ITN that happens to include a blank optional field (`custom_str1`-`5` etc, common when unused).
